## 1. 제품 한 줄 정의

> **Discord를 개발자의 서버 운영 콘솔로 만든다.**

단순히 "Discord에서 서버 상태를 보여주는 봇"이 아니라, 아래 4가지가 결합된 제품으로 정의한다.

- **Monitoring** — 서버/애플리케이션 지표 수집
- **Alerting** — 이상 상태 감지 및 알림
- **Observability** — 장애 이력·원인 추적
- **Developer SDK** — 코드 한두 줄로 연동되는 수집 도구

개발자가 서버에 SDK를 추가하면, 그 서버의 상태 확인 · 장애 알림 · (장기적으로) 운영 명령까지 Discord 안에서 모두 처리할 수 있는 서비스로 발전시킨다.

---

## 2. 배경 및 문제 정의

기존 모니터링 서비스는 대부분 다음과 같은 구조를 갖는다.

```text
서버 → Agent / SDK → Monitoring Server → Web Dashboard
```

지표를 확인하려면 사용자가 별도의 웹 대시보드에 접속해야 하며, Discord 알림은 대부분 "보조 채널" 수준으로만 제공된다. 단순히 "Discord에 CPU 수치를 보여준다"는 정의만으로는 기존 서비스의 Discord 알림 연동(Webhook Integration)과 차별화되지 않는다.

따라서 이 제품은 Discord를 부가 알림 채널이 아니라 **주 운영 인터페이스**로 삼는다.

```text
서버 → SDK → Monitoring Server → Discord
```

개발자는 별도 대시보드 없이 이미 사용 중인 Discord 서버에서 바로 상태를 확인한다. 이 구조 자체가 제품의 핵심 차별점이다.

## 5. 핵심 기능 명세

### 5.1 Developer SDK

SDK는 이 서비스의 핵심 기능으로 취급한다. 목표는 "설정 없이 붙이면 동작"하는 수준의 간결함이다.

**Express (Node.js)**

```js
const monitor = require("@service/express");

app.use(monitor());
```

**Spring Boot**

```gradle
implementation("com.example:monitor-spring-boot-starter")
```

SDK가 자동으로 수집하는 정보:

```text
CPU, Memory, Disk, Process, HTTP, Latency, Error, GC, Event Loop, Uptime
```

### 5.2 모니터링 대상

**기본 (MVP 범위)**

```text
CPU / RAM / Disk / Uptime
HTTP Health Check / Response Time / Error Rate
```

**DB 연동 (확장)**

지원 대상: MySQL, PostgreSQL, MongoDB

```text
MySQL
Connection: 🟢
Latency: 4ms
Connections: 18/100
Slow Queries: 2
Errors: 0
```

**Redis 연동 (확장)**

```text
Redis
Connection: 🟢
Latency: 1ms
Memory: 412MB
Hit Rate: 94.2%
Connected Clients: 12
```

**API 단위 metric (확장)**

```text
GET /users       123ms
POST /login        82ms
GET /products      41ms
```

### 5.3 CI/CD 상태 연동 (Code Base 기능)

초기 범위는 코드 분석이 아니라 **CI/CD 파이프라인 상태 표시**로 제한한다. AI 코드 분석·전체 코드 분석은 범위에서 제외한다.

```text
Commit / Branch / Build / Test / Deployment
```

```text
Code

Commit: a82c91f
Branch: main
Build: 🟢
Tests: 248/248
Deploy: 2m ago
```

배포 실패 시:

```text
🔴 Deployment Failed

Commit: 82a91f
Tests: 231/248
Build time: 42s

Error:
TypeError: Cannot read properties of undefined
```

이를 통해 "Monitoring + CI/CD 상태 확인"이 하나의 제품 흐름으로 이어진다.

### 5.4 Discord 메시지 방식

주기적인 상태 갱신은 **기존 메시지를 수정(edit)하는 방식**을 기본으로 한다. 매 갱신마다 새 메시지를 보내면 채널이 로그로 도배된다.

```text
[✓] 기존 메시지 수정          ← 기본값
[ ] 새 메시지 생성
[ ] 이상 상태에서만 새 메시지 생성
```

### 5.5 이상 탐지 및 알림

단순 임계값뿐 아니라 **지속시간 조건**까지 지원한다.

```text
CPU > 80%
RAM > 90%
Disk > 85%
API latency > 500ms
HTTP error rate > 5%
DB latency > 100ms
Redis disconnected
```

지속시간 조건 예시:

```text
CPU > 80% AND 5분 지속
HTTP 5xx > 5%
API DOWN
```

알림 전달 채널:

```text
Discord Channel / Role Mention / User Mention / DM / Webhook
```

### 5.6 장애 이력 (Observability)

현재 상태만 보여주는 것을 넘어 **장애 이력을 저장**하면 제품 가치가 크게 상승한다.

```text
/incidents

최근 장애

🔴 API
08/23 01:42 ~ 01:49
7분 12초

원인:
Database connection timeout

영향:
HTTP 5xx 13.2%
```

저장 데이터 항목 (확장 시): `Uptime, Downtime, Incident, Recovery Time, Error Rate, Latency, CPU, Memory`

이 기능을 통해 단순 Discord Bot이 아니라 **Observability 서비스**로 포지셔닝한다.

### 5.7 Discord 명령어 (운영 콘솔화)

장기적으로 Discord 자체를 운영 콘솔로 만든다.

```text
/status
/metrics
/logs api 50
/incidents
/deployments
```

장기 로드맵에서는 `/restart api` 와 같은 원격 명령까지 지원한다. 단, **모니터링과 원격 제어는 권한 체계를 반드시 분리**한다 (7장 참고).

## 6. 보안 설계

SDK 기반 서비스는 토큰 유출 시 데이터 위조·시스템 영향 등의 리스크가 크므로, 최소한 아래 토큰을 분리한다.

```text
Project ID
Write Token     (SDK → 서버로 metric 전송)
Read Token      (Discord/대시보드에서 조회)
Command Token   (원격 명령 실행 전용)
```

권한 흐름을 명확히 분리한다.

```text
Monitoring  → 읽기 / metric 전송
Command     → 재시작 / 명령 실행
```

특히 원격 명령 기능은 모니터링 API와 **완전히 별도의 권한 체계**를 사용한다.

## 10. 경쟁력 및 차별화 전략

단순 기능 비교("Discord에서 CPU를 보여준다")로는 기존 모니터링 서비스의 Discord Integration과 차별화하기 어렵다. 차별점은 아래와 같은 **End-to-End 경험**에서 나온다.

```text
SDK 설치
↓
자동 Metric 수집
↓
Discord에서 상태 확인
↓
Discord에서 장애 알림
↓
Discord에서 장애 이력 확인
↓
Discord에서 배포 상태 확인
↓
Discord에서 운영 명령
```

따라서 제품 설계의 중심은 Discord Bot 자체가 아니라 다음 조합이다.

```text
Developer SDK + Monitoring + Observability + Alerting + Discord Interface
```

Discord는 단순 알림 채널이 아니라 **제품의 주요 인터페이스**다.
